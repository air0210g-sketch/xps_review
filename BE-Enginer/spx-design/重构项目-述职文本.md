## 详细表达文本

### ① 一句话定位

> 我参与的是 SPX 末公里的架构重构项目。**在不中断业务迭代的前提下**，通过**架构拆分、领域解耦与 Python→Go 迁移**，实现了系统性能与资源的大幅优化、域间依赖与发布风险的降低、以及系统稳定性的提升。技术难点在于**从强一致到最终一致的模型升级、多源更新的流程终结设计、以及 350+ 接口的平滑迁移与切流**。

---

### ② 业务背景与目标

> **痛点**：2022 年之前，为适配快速业务迭代，后端使用 Python 开发，所有模块共用一个代码仓库，通过目录隔离。随着业务复杂度和体量上升，暴露出四个核心问题：

| 维度 | 具体表现 |
|------|---------|
| **性能与资源** | Python 性能有限，难以支撑业务发展，需投入大量服务器资源 |
| **依赖与耦合** | 各模块直接引用，依赖关系错综复杂 |
| **协作与发布** | 共仓并行开发时代码冲突严重，发布风险高 |
| **数据一致性** | 强依赖 FO 状态机，并发场景（如 onhold 下 redelivery + hub receive）易出现数据不一致，需频繁 datafix |

> **目标**：在不中断业务的前提下完成三项升级——**服务拆分**（大单体→微服务）、**解耦与一致性模型升级**（强一致→最终一致）、**语言迁移**（Python→Go）。

---

### ③ 三路推进架构总览

> 重构分三路并行推进：

| 路线 | 核心内容 | 关键设计 |
|------|---------|---------|
| **架构升级** | 按作业域拆分微服务（站内/Order/Pickup/Delivery/LH），独立部署治理 | Facade/HTTP 边界，消除共仓直接引用 |
| **解耦与一致性** | 用 Plan + 事件驱动替代 FO 状态机强依赖，域内状态机 + 最终一致 | AT/TO 解耦、Cancel Plan 终结、DDD 聚合根 |
| **语言与工程** | Python 核心服务迁移至 Go，平滑切流并下线 Python | 读对比（≥99.99%）+ 接口维度灰度 |

> 数据流关键路径：站内轨迹 → eventServer 写 Kafka → dispatchServer 消费后下发 cancel/update Plan → deliveryServer 消费 Plan 执行域内流程；FO 直接消费 Kafka topic，按 mtime 比较更新状态，保障最终一致。

---

### ④ 核心技术难点

#### 难点 1：从强一致到最终一致的模型升级

**问题**：

> 原架构中，所有作业域强依赖 FO 状态机做一致性校验。并发场景下（如 onhold 订单同时触发 redelivery 和 hub receive），FO 状态校验会产生冲突，导致数据错乱和业务阻塞，需要频繁人工 datafix。

**方案——Plan + 事件驱动**：

> | 层级 | 机制 | 解决什么 |
> |------|------|---------|
> | **域内** | Plan 生命周期内仅使用 **LM 域内状态机**，不再依赖 FO 状态机 | 消除域间强耦合 |
> | **对外** | 域内完成后只发送事件/轨迹，FO 按事件 **mtime** 顺序更新 | 保证最终一致，消除并发冲突 |
> | **控制面** | 由**调度中心**下发 Plan、控制灰度；**轨迹中心**接收消息做点对点推送 | 统一调度与可观测 |
>
> **DDD 实践**：按限界上下文划分子域（派送任务管理/骑手派送/财务支付/订单/路径规划），以 **DeliveryOrder** 为聚合根控制派送行为，完成派送/OnHold 时发送领域事件驱动上游更新。
>
> **一句话总结**：Plan 生命周期内域内自治 + 事件驱动 FO 按 mtime 更新，从强一致改为最终一致，消除并发数据错乱。

---

#### 难点 2：多源更新与 Cancel Plan 终结流程

**问题**：

> 解耦后，AT（Assignment Task）/RAT 与 TO（Transport Order）的关系变得复杂——需要在 Cancel Plan 时正确终结域内流程，同时支持重入；骑手操作与运单状态也需要解耦。

**方案**：

> - **AT/RAT 与 TO 解耦**：通过「是否有 Plan」判断走新架构或老逻辑，实现新旧兼容。
> - **Cancel Plan 终结流程**：**先终结 DO，再 unlink AT/RAT**，支持重入。若先 unlink 则重入时无法确定订单归属，会导致状态错乱。
> - **骑手与运单解耦**：有 Plan 时，骑手操作通过轨迹推送更新，不直接改 TO 状态。
> - **切流控制**：由调度中心按 **Plan 类型 + 站点 + 订单号百分比** 控制灰度切流。
>
> **一句话总结**：Cancel Plan 先终结 DO 再 unlink，支持重入；骑手与运单通过轨迹解耦，调度中心统一控切流。

---

#### 难点 3：350+ 接口的 Python→Go 迁移与切流

**问题**：

> 核心服务从 Python 迁移到 Go，涉及大量接口。如何保证迁移后功能完全一致？如何在日常迭代不停的情况下平滑切流？

**方案——读对比 + 接口灰度**：

> | 阶段 | 策略 | 关键细节 |
> |------|------|---------|
> | **读对比** | 双读 Python 和 Go，对比结果 | 一致率 **≥99.99%** 后才切流；需支持灰度对比（大流量全量对比会压垮 DB/Redis/MQ）；支持忽略字段（读后即写导致异步对比误报） |
> | **写灰度** | 按比例由小到大灰度 | 比例用**随机数**控制（避免按 driver 等业务 key 导致流量不均）；写接口灰度前需 review 两边实现一致 |
> | **切流顺序** | 对比 → Python 转发 → 客户端读配置 → 直连 Go | APP 鉴权仍走 Python，Admin 对接权限系统并做服务可降级 |
> | **配置管理** | 接口维度灰度 | 通过 `delivery.refactor_release`（path → 转发百分比）、`delivery.refactor_data_comparison`（需对比的 URL）配置 |
>
> **一句话总结**：读对比 99.99%+ 再切流 + 随机数比例灰度 + 接口维度配置，保障 350+ 接口平滑迁移。

---

#### 难点 4：长尾治理与并行需求风险

**问题**：

> 约 **20% 的长尾事项**（新接口、下线接口、依赖扯皮等）会占用约 **80% 的时间**（23Q1～Q3）。重构与业务需求并行时，信息不同步、实现不一致的风险很高。部署架构差异（如 live 与 nolive 使用不同 Redis 集群）也会导致测试环境正常但线上异常。

**应对策略**：

> - **计划预留**：Plan 阶段预留长尾时间，避免低估 20/80 问题。
> - **对齐部署差异**：提前对齐 live/nolive 的 Redis 集群、Saturn/权限树/MySQL/Apollo 等配置，避免漏配导致线上异常。
> - **并行需求管理**：重构与业务需求同步变更，在方案中写清相互影响；写接口灰度前 review 两边实现一致。
> - **提供新接口**：对新旧接口并存的情况，直接提供新接口实现，而非搞复杂的新旧转换层。
>
> **一句话总结**：预留长尾、对齐部署、同步变更、写灰度前双边 review，管控并行风险。

## 追问预判与应对要点

| 可能的追问方向 | 关键回答要点 |
|---------------|-------------|
| **为什么从强一致改为最终一致？** | 并发场景（redelivery + hub receive）下强校验易阻塞；事件驱动 + FO 按 mtime 更新可保障顺序与最终一致，消除 datafix |
| **Cancel Plan 为什么先终结 DO 再 unlink？** | 支持重入——若先 unlink，重入时无法确定订单属于哪个骑手，导致状态错乱 |
| **读对比为什么要 99.99%+？** | 保证切流前数据与 Python 完全一致，降低风险；大流量接口需灰度对比避免压垮链路 |
| **灰度为什么用随机数而非 driver？** | 按 driver 等业务 key 会导致流量分布不均、难以精确控制比例；随机数控制更稳定 |
| **长尾为什么占 80% 时间？** | 约 20% 事项（新接口/下线接口/依赖扯皮）会贯穿整个项目周期（23Q1～Q3），Plan 阶段必须预留 |
| **DDD 怎么落地的？** | 按限界上下文划分子域，DeliveryOrder 为聚合根控制派送行为，完成/OnHold 时发领域事件驱动上游更新 |
| **FO 按 mtime 更新如何保证顺序？** | FO 直接消费 Kafka topic，比较当前 FO mtime 与消息 mtime，只有 msg mtime > FO mtime 时才更新 |
| **部署差异导致的问题？** | live 与 nolive 用不同 Redis 集群，nolive 测试正常但 live 异常；提前对齐部署架构可避免 |
